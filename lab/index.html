Retail Analytics Lab

A production-shaped analytics pipeline over 1,067,371 real transactions from the UCI Online Retail II dataset — the same data behind Chen et al.'s RFM segmentation paper. Data contracts at every stage boundary, an auditable cleaning ledger, a DuckDB star schema, and independent Python, SQL and base-R implementations, with RFM also checked through a pure-Python browser port.

The R and Python below are not screenshots. They compile and execute in your browser via WebAssembly, on real data, and you can edit them.

01 — PROVENANCE

The data, and where it actually comes from

Transactions from a UK-registered, non-store online giftware retailer between 1 December 2009 and 9 December 2011. It is the dataset behind Chen, Sain & Guo (2012), "Data mining for the online retail industry: a case study of RFM model-based customer segmentation" — which is why RFM is the analysis this lab implements: the method and the data belong together in the literature.

Provenance is enforced, not asserted. The pipeline verifies the source file's SHA-256 against a committed sidecar before reading a single row. If the upstream file is ever swapped, the run aborts instead of quietly analysing different data. Source: the onlineretail2 R package, which redistributes the UCI data with the donor's (Dr Daqing Chen) permission for non-commercial use.

Five stages, each with a contract on its output

    07 — THE PARITY HARNESS
    
Two languages, one answer — checked in front of you

    
This is the part of the project I would actually defend in an
    interview. RFM is implemented four ways and cohort retention three ways across
    different execution models, with tests over comparable outputs. It is what catches
    definitional drift — a different recency convention, a different tie rule, day
    arithmetic instead of calendar months — which no single-language test can see.

  

  

    

      
      idle
    

    
Runs both runtimes on the same sample and compares all 5,852-customer columns element by element.

  

  

    

      
The tie trap this rule exists to avoid

      
The obvious way to score RFM is NTILE(5) in SQL,
      pd.qcut in pandas, cut(quantile(…)) in R. All three claim to make
      quintiles. All three disagree on this data, because roughly 40% of customers have
      frequency = 1 — and NTILE splits a run of tied values across bucket
      boundaries by row order. Two customers who behaved identically get different
      scores, and which one gets the better score depends on how the rows happened to sort.

      
The fix is to define scores on values, not row positions:

      
breaks = quantile(x, [.20,.40,.60,.80])   # type 7
score  = 1 + #{b in breaks : x > b}       # ascending
score  = 5 - #{b in breaks : x > b}       # descending

      
Tied customers now always score the same, in every language. The cost
      is that quintiles are no longer exactly equal-sized where ties straddle a boundary —
      which is the honest outcome, not a defect.

    

    

      
Defects this harness actually found

      
    
        
  • A one-day recency disagreement. Python
        subtracted raw timestamps, so a purchase at 13:00 on 9 Dec was 0 days from a
        10 Dec reference; SQL and R worked on dates and said 1. That silently moved
        customers across an r_score boundary. Fixed at the definition — recency is
        whole calendar days — not with a tolerance in the test.
    • 
        
  • A silent 3,393-row drop. The returns
        finaliser was discarding zero-value write-off lines without recording them.
        The ledger now accounts for them explicitly.
    • 
        
  • Month arithmetic. 31 Jan → 1 Mar is 29 days but two calendar months.
        Day-difference ÷ 30.44 drifts by a whole index over a two-year window; the
        cohort index is computed as 12·Δyear + Δmonth in all three implementations.

    09 — THE SQL LAYER
    
Star schema and analytical SQL

    
DuckDB rather than SQLite, because the analysis leans on window
    functions, QUANTILE_CONT, MODE and list types — and because an embedded
    columnar engine is the honest choice for a 1M-row analytical workload that has to run
    from a laptop with no server. Grain is declared per table; four referential and
    arithmetic integrity checks run after every build.
